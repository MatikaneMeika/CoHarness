# 多 harness 派发使用说明

> 适用对象：用 `03-multi-harness-project` 骨架实例化的项目。
> 库侧（CoHarness 本体）只管**认领、工作树、拉起、执法**四件事；派发本身是**去中心**的——
> 谁收工谁唤醒下一个，总控不独占派发按钮。本文与 `.agent/dispatch.md`、`RFC-0003`、
> `RFC-0004` 口径同源，数字与命令以实际脚本为准。

## 0. 一句话理解派发

一次派发 = **认领**（`wsc claim`，原子提交到 `main`）+ **建工作树**（原生
`git worktree add -b coh/<卡号> <项目名>.wt/<卡号>`）+ **开新终端**拉起目标 harness。
拉起后立刻**失联**：不持有句柄、不读子进程输出、不记运行时状态——所以没有常驻进程，
杀掉 CoHarness 也不丢状态（状态在 git 与卡片里）。

## 1. 前提

- 项目由 03 骨架实例化，本地钩子已装（裸克隆后跑一次 `wsc sync` 补装）。
- 卡片在 `backlog/tasks/`，frontmatter 带 `labels: [role:<角色>]`（所有权执法要用）。
- `.agent/dispatch.md` 在位——它是项目侧的"角色 → 启动命令"表。

## 2. 第一步：architect 登记候选 harness（只读探测）

**骨架不预置任何本机 CLI 名称、可执行文件路径或环境位置。** 由 `architect` 在本机 PATH 探测后，
或按用户明确指定的工具名，填写 `.agent/dispatch.md` 的候选 JSON 块：

```json
{"harnesses": [{"name": "codex", "probe": "codex"}]}
```

- `probe` 只做 PATH 存在性检查，**不承诺**该 CLI 支持无头派发。
- 候选清单是**环境事实**；角色映射是**项目策略**——两者分开，候选可用不等于自动改派。

## 3. 第二步：architect 填角色启动命令表

同一文件里把角色映射到 CLI，命令支持 `{worktree}` 与 `{card}` 占位符，拉起前替换为工作树绝对
路径与卡号：

| 角色 | 启动命令 |
|---|---|
| pm | `<harness-cli> --cd {worktree}` |
| coder | `<harness-cli> --cd {worktree}` |

- 一个角色一行；同一角色写重复时后写的生效。
- 新 harness 是否承担某角色必须走规则卡 / ADR，**不自动映射**。
- 工具不在 PATH 时面板标灰，强行派发响亮失败。

## 4. 第三步：只读体检

```bash
python scripts/dispatch_env.py            # 人类可读
python scripts/dispatch_env.py --json     # 机器可读，字段稳定
```

输出字段：`auto_dispatch`、`available`、`missing`、`roles`、`unmapped`、`unready_roles`。

退出码：

| 码 | 含义 |
|---|---|
| `0` | 所有已配置角色就绪 |
| `1` | 存在缺工具的已配置角色 |
| `2` | 候选清单或启动命令表缺失 / 格式错误 |

该脚本**只读**：不执行候选 CLI、不联网、不写项目文件。

## 5. 第四步：派发

两种入口：

```bash
coh-dispatch --advance <项目>     # 无面板：认领 + 建工作树 + 开新终端，拉起后失联
coh-panel                         # 全屏四页：项目 → 任务 → 卡详情 → 派发
```

派发页（任务页按 `d`）：

- 候选 = 依赖就绪、边界不与在做卡冲突的 `todo` 卡；
- 系统按确定性规则预选（卡号最小），`↑↓` 改选，`Enter` 派发，`m` 只印命令不执行，`r` 原地重试。

动作序列与失败语义：

1. 认领 `wsc claim`（原子提交到 `main`，先到先得）；
2. 建工作树 `git worktree add -b coh/<卡号> <项目名>.wt/<卡号>`；
3. 开新终端拉起目标命令（cwd = 工作树）；
4. 拉起后立刻失联。

## 6. 自动派发开关（默认关闭）

- **默认关闭**：收工协议不会自动唤醒下一个 harness。
- 只有**用户明确**对 `architect` 或 `integrator` 说「**开启自动派发** / **关闭自动派发**」，
  该角色才更新 `.agent/dispatch.md` 里的 `自动派发：开启 / 关闭` 行。
- 候选可用 ≠ 自动派发已开启；角色不得自行推断，也不得替用户翻这个开关。

## 7. 失败处置

- 认领失败、建树失败、开窗失败：**不重试、不静默改派**——由发起会话重试一次，到顶升级给人。
- 失败信息包含命令（argv 参数列表，不裸拼 shell 字符串）与退出码，直接打印，便于定位。
- 总控不在场就停在原地，靠下一次 `wsc sync` 巡检恢复，**不引入常驻进程**。

## 8. 排错速查

| 现象 | 可能原因 | 处置 |
|---|---|---|
| 面板只列候选、不执行 | 缺 `.agent/dispatch.md` 或缺角色命令 | 补表 |
| `dispatch_env.py` 退出 2 | 候选 JSON 块缺失 / 坏 JSON / 缺角色表 | 按提示补 |
| 角色标灰 / `unready_roles` 非空 | 启动命令的 CLI 不在 PATH | 装 CLI 或改表 |
| 建树失败 | 路径被占 / 分支已存在 / 不是同一项目 | 看 argv + 退出码定位 |
| 派发后没窗口 | 终端不支持 / 命令写错 | 用 `m` 只印命令，手工跑一遍 |

## 9. 边界

- 库侧不引入常驻进程、不做服务端、不读子进程输出。
- 展示面**默认只读**；派发是唯一写路径。
- worktree 管理交给**原生 git**：worktrunk（`git-wt`）当前不参与 dispatch 建树——其
  `switch -c` 只能建到 `../<repo>.<branch>`，无法满足 `<项目名>.wt/<卡号>` 的路径契约。
- 远端门禁（CI）是第二道门，口径见 `docs/rfcs/RFC-0004-远端门禁.md`。
