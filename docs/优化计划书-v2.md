## 0. 读法与边界

**这份文档是什么**：继 W1–W14 之后的第二份工作计划。W1–W14 把骨架库从"自制任务系统"带到了
"发布链全闭的 v1.2.3"（PyPI 官方源实测，`docs/CHANGELOG.md:26`）；本份回答"然后呢"。三个方向的
取舍已经过**外部竞品全景**与**内部规划档案**双向核实（证据快照见附录 B），落成九个工作项加一条
并行运营轨。

**这份文档不是什么**：不含"计划书作者亲做"的环节。每项都写成给执行者（人或 harness）的操作规程
与验收标准。执行者按本仓库自己的纪律干活——骨架本体新能力走 RFC 路线，真实摩擦走
`.agent/improvements.md` → evolve 晋升管线，一个改动一个 commit；测试条数、行数、文件数一律以实跑
与既有钉子为准，本文出现的具体数字均为 2026-10-02 快照。

**编号与书写约定**：

- 工作项 W15–W23 续 `docs/优化计划书.md` 的 W 序列；决策记录全局唯一、落在
  `docs/EVOLUTION-PLAN.md`（只增不改，推翻旧条=追加新条注明取代关系），本份新决策从 ADR-12 起。
- 旧份以对话摘录形态入库（`\#`、`\*\*` 转义与【turnXsearchY】引用占位未剥），本份按仓库正常
  Markdown 书写；**不回改旧份**——它已被 ADR-10 当作"被回绝的对照表"引用，是裁决证据的一部分。
- **星标数字是证据快照，会腐烂**：可以出现在本计划书与验收记录里，**禁止**复制进 README /
  AGENTS.md 这类长期承诺文档——对外对比一律按机制写，不按星数写（沿用"数字由实跑给"的既有口径）。

**排序原则**：阶段一（发布收口 v1.3.0）→ 阶段二（远端门禁，两步走）→ 阶段三（集成验证清欠）。
阶段三与阶段二无依赖可并行；阶段二内部 W19 必须先于 W20（RFC 先行、执法面后动）；W21/W22 若要
动 `check.py`，排在 W20 之后（行数预算一次规划）。

## 1. 形势判断：为什么是这三件事

### 1.1 外部格局：三层分工与中间的空洞

2026-10-02 经 GitHub API 实测的快照（核对命令与长尾名单见附录 B）：

| 层 | 代表项目 | 星标 | 管什么 | 不管什么 |
|---|---|---|---|---|
| 编排器 | stablyai/orca | 83,426 | 并行代理"舰队"的桌面/移动运行时 | 仓库里的约定 |
| 编排器 | manaflow-ai/cmux | 27,559 | 多代理终端（Ghostty 基座） | 同上 |
| 编排器 | smtg-ai/claude-squad | 8,561 | tmux + worktree 管多个终端代理 | 同上 |
| 编排器 | stravu/crystal（已更名 Nimbalyst） | 3,123 | 桌面多会话 worktree；半年未推送 | 同上 |
| 规范层 | affaan-m/ECC | 270,854 | 跨 harness 技能/记忆/安全注入 | 代理之间的边界 |
| 规范层 | github/spec-kit | 139,753 | SDD 规格流程（本项目 03 骨架的可选依赖） | 同上 |
| 规范层 | Fission-AI/OpenSpec | 70,891 | SDD 变体 | 同上 |
| 规范层 | agentsmd/agents.md | 24,734 | AGENTS.md 开放格式（本项目约定的载体） | 同上 |
| 看板/派发 | BloopAI/vibe-kanban | 28,240 | 给代理派卡的看板；**已宣布 sunset** | —— |
| 协作执法 | （本项目）CoHarness | 2 | 多个异构 harness 同仓的边界/认领/执法 | 进程隔离（有意不管） |

**空洞在哪**：编排器解决"隔离与并行"，规范层解决"单个代理怎么干活"；而"多个异构 harness 在
同一个仓库里不打架"——路径所有权、认领串行化、改动挂卡、卡边界互斥的**机械执法**——没有任何
高星项目在做。最近似的 ZEST-im/vibe-engineering（kanban + scope 边界 + 测试门禁）6 星；
FelipeCarillo/holoctl（项目结构编译到多工具，思路同本项目的 adapters 薄指针）1 星。CoHarness 的
`check.py` 执法 + `wsc claim` 原子认领 + 单写者所有权表（规则层写者行
`03-multi-harness-project/AGENTS.md:33`）是这个空位里唯一成形的实现。**既是机会（细分空着），
也是警示（2 星说明发现渠道没打开）。**

**两个市场信号**：

1. **vibe-kanban（28,240 星）已 sunset**——README 顶部横幅原话 "Vibe Kanban is sunsetting."
   （公告指向 vibekanban.com/blog/shutdown，未推荐迁移目标；仓库未归档，末次推送 2026-09-19）。
   它退出留下的用户群恰是 CoHarness 的对位人群：要"卡驱动派发"，但不要服务端与本地应用库。
   本仓库 `README.md:178` 的 sunset 记录**属实**（本轮核实，详见附录 B），无需修改。
2. **编排器向上侵蚀的信号**：Claude Code 原生 agent teams、oh-my-codex 的 hooks/teams 表明编排器
   可能内建约定功能。CoHarness 的防御是把定位写清：**工具无关的协议层**——编排器拉起的每个代理，
   其仓库可以携带同一份 AGENTS.md 与 check.py。这不是竞争，是共生。

**结论**：对外，定位声明（W17）与发布（W18）是当前最高杠杆——产品差异真实存在，但没有被看见。
对内，"机械执法"这个品牌承诺还有一个没闭的口子：本地钩子可被 `--no-verify` 绕过、第二台机器
裸克隆时钩子缺席——只有远端门禁（W19/W20）能把执法从"君子协定"升格为"仓库事实"。

## 2. 阶段一：发布收口 v1.3.0（W15–W18）

### W15 CI 偶发红取证与闭口

**背景**：项目状态里唯一未闭口的质量项。历史上五类真因已修：git 后台维护竞态（CHANGELOG :29）、
浅克隆假红（:11）、Windows 8.3 短名（:69）、cp1252 控制台编码（:9）、macOS 符号链接（:8）。
当前"那条偶发红"指仍未归因的残余——不取证就修，修的可能是想象中的病。

**现状**：`.github/workflows/ci.yml` 五个 job（stdlib 3 OS × 3 Python 共 9 腿、oracle 差分预言机、
first-run 计时、push-gate 端到端、security）。first-run 阈值 >300s 判红，实测 ubuntu 2140ms /
windows 2228ms（CHANGELOG :63），距阈值两个数量级，但 runner 网络抖动可能拉高依赖安装与 git
操作耗时——这是首要嫌疑，其次是 Windows 腿的偶发文件锁。

**实施形状**（取证规程，执行者照做）：

1. `gh run list --workflow=ci.yml --limit 50 --json conclusion,createdAt,databaseId,displayTitle`
   拉最近 50 轮，筛出非 success 的 run。
2. `gh run view <id> --log-failed` 逐个拉失败腿日志，按 (job, OS, Python, 用例名) 分类归并。
3. 可复现的：本地按同矩阵参数重演（`python -m unittest tests.test_xxx`）；不可复现的：记录
   出现频率与时间分布，开连续观察窗口。
4. 修复优先于豁免；确属 runner 环境问题（如平台侧网络）才允许豁免，豁免必须成文：判据改确定性
   （参考 :29 的先例——从源头关闭 git 后台维护，而不是给 rmtree 加重试）。

**验收清单**：

- [ ] 连续 10 轮 CI 全绿（或覆盖 ≥2 周，取先到），期间无 unexplained fail
- [ ] 若结论是环境问题：`docs/audits/` 有取证链记录 + 判据的确定性豁免及理由；**不接受"再观察观察"这种无终态结论**
- [ ] 若修改了 ci.yml 或测试基建：红绿对照可复现，CHANGELOG 记一条 [缺陷修复]

**风险与回退**：偶发红若源自 first-run 计时阈值，调阈值必须带 ≥10 个样本的耗时分布数据，不许
拍脑袋放宽；CI 文件改动本身也要过 `push-gate` job（改动会不会破坏端到端演练）。

### W16 派发失败路径测试钉子

**背景**：HANDOFF §1.4-F 与 §3.1 的两条测试欠账。`dispatch.launch` 的动作序列是
认领（`wsc claim`，会提交并推 main）→ 建工作树 → 开新终端，每一步都可能失败；失败路径目前
只有实现、没有钉子——没有钉子的行为约定，下一次重构就会悄悄变样。

**现状**：`tests/test_dispatch.py` 38 条（CHANGELOG :13），覆盖 plan / 候选 / 阻塞 / 拉起；
无失败注入用例。`dispatch.py` 300/300 顶格（`tests/test_distribution_surface.py:44-48`）。
HANDOFF §1.4-C 已明示"无回滚是有意设计"。

**实施形状**：

1. 用例 A「建树失败」：注入失败（monkeypatch `_worktree` 的子进程返回非零，或传已占用的非法
   路径），断言：错误信息诚实（含命令与退出码，不吞 stderr）、无半途脏状态（不留半套 worktree
   登记、不动别的卡）。
2. 用例 B「认领成功但建树失败」端到端：断言卡状态确实停在 `doing`、无自动回滚、看板如实显示
   在做——**钉现状为有意设计**（测试名与 docstring 援引 HANDOFF §1.4-C），这是行为契约卡，
   不是缺陷修复卡。
3. 若实现与 HANDOFF 描述不符（例如抛未捕获异常而非干净失败）：先钉**真实行为**并记录差异，
   是否修另立缺陷卡——测试钉的是协议承诺，不是愿望。

**验收清单**：

- [x] 两条用例对实现改动可证红绿（注入失败前后各跑一次）
- [x] 全量自测绿（`python -m unittest discover -s tests`，条数以实跑为准）
- [x] `dispatch.py` 不超 300 行；若为钉子必须改实现，改动是独立缺陷修复 commit + CHANGELOG 条目

**风险与回退**：用例 B 若揭示真缺陷（崩溃而非干净失败），按边界规则先报告（卡上留审阅意见）
再决定修法，不许顺手扩 `dispatch.py` 行数预算。

### W20 `--against <ref>` 基线 diff 执法

**背景**：pre-commit 的 `--diff` 判**暂存集**（`check_diff`，`check.py:544` 起）；CI checkout
出的是干净树、没有暂存集——"改动必须挂卡"这条执法在 CI 形态下需要显式基线，否则远端门禁只能
拦非法看板与坏文件名，拦不住卡外改动。

**现状**：`check.py` main() 五个 flag（:715-756）；760/760 顶格（LINE_BUDGET，
`tests/test_distribution_surface.py:44`）；历史上两次上调均有成文理由（650→700 为 I-005 所有权
执法，:34；700→760 为 v1.2.0 五机制，:38-39）——**先例程序**是"独立 commit + 预算注释写理由 +
CHANGELOG 记一条"。

**实施形状**：

1. **重构不改行为**：把 `check_diff` 拆成"变更集提供者 + 判定核心"（判定核心 = 覆盖判定 /
   forbidden 优先 / 自授权豁免）。现有 flag 走暂存集提供者；**全量既有用例零改动仍绿**是重构
   安全判据。
2. 新增 `--against <ref>`：变更集 = `git diff --name-status <ref>...HEAD`（改名连旧路径一起
   过所有权表，与 I-005 同口径），喂给同一判定核心。**不写第二套口径**（宪法：判定不另写一套）。
3. 失败语义：ref 不存在 / 无合并基 → 响亮失败（exit 1 + 明确报错与自查命令），绝不静默按空集
   全绿（ADR-10 决定 1 同精神：留空和写错是两回事）。
4. 行数预算：760→820（+60）独立 commit，`LINE_BUDGET` 注释写理由（第三次上调：远端 diff 执法
   必须长在随骨架分发的单文件里，与 I-005/v1.2.0 两次先例同性质），CHANGELOG 记一条。
5. workflow 升级：`pull_request` 触发时 `--against origin/main`（`fetch-depth: 0`）；`push`
   触发时 `--against ${{ github.event.before }}`；`event.before` 为全零（首推/强推）时**降级**
   只跑 `--names --tasks` 并发 `::notice` 声明降级——降级必须可见，不许静默。
6. 测试三类（`tests/test_check_current.py`）：卡外改动被拦 / 挂卡放行 / 基线缺失响亮失败。
7. RFC-0004 追记第二决策节：为何 push 事件用 `event.before`、强推为何降级不硬拦（协议本就禁
   强推，门禁不做第二裁判）、merge commit 下 `ref...HEAD` 语义的已知边界。

**验收清单**：

- [x] 三类用例红绿可证（对实现改动前/后各跑）
- [x] 既有 check 测试**零改动**全绿（重构不改行为的硬门）
- [x] LINE_BUDGET 注释与 CHANGELOG 条目在位；check.py 实测 ≤820
- [ ] 真机：临时仓库推一例卡外改动的 PR，CI 红且日志能定位到卡（提示含卡号/路径）

**风险与回退**：判定核心重构若引起既有行为漂移，回退重构而非阉割用例；`ref...HEAD` 在极端
rebase 场景的边界写进 RFC 已知边界节，不在代码里打补丁式特判。

### 3.3 ADR-12 与 RFC-0004 成文骨架（给执行者）

**分工**：ADR 记架构层取舍（执法面的分发位置与行数决策，落在 `docs/EVOLUTION-PLAN.md`）；
RFC 记单个能力的取舍与代价（触发器形态、降级语义，落在 `docs/rfcs/RFC-0004-远端门禁.md`）。

**RFC-0004 必写的替代方案表**（"没有替代方案的 RFC 不是 RFC，是通知"——`docs/rfcs/README.md:18`）：

| 替代方案 | 否决理由 |
|---|---|
| CoHarness 侧在线门禁服务 | 违反零服务端 / 文件即真相（宪法第 1、2 条）；本计划 §1.3 新纪律 |
| 只靠分支保护 required check | 它保证"有个绿 check"，不保证跑的是本项目执法；写成"装机后建议"，不是骨架能力 |
| 只加 PR 模板纪律（已有，禁 `--no-verify`） | 约定不是机制——这正是本 RFC 要补的口子 |
| CI 全量跑 check.py 不加 `--against` | CI 干净树无暂存集，`--diff` 空转，"挂卡"执法缺席——所以 W20 必要 |

**ADR-12 决定要点**：workflow 文件随 03 骨架分发（01/02/04 不带）；零代码版先立 `--names/--tasks`
门禁，`--against` 补 diff 执法；CI 一律 `--no-track`（runner 遥测无意义）；非 GitHub 托管惰性
无害；check.py 行数 760→820（第三次上调，先例程序成文）。

**是否另立 ADR-13**：按先例（前两次上调只记 LINE_BUDGET 注释 + CHANGELOG），**不另立**；若 RFC
评审认为远端门禁改变了"执法面单文件随骨架分发"的架构语义，再升格 ADR-13——留给评审时定，
本计划不预支。
