# EVOLUTION-PROCESS — 骨架自我迭代管线

> 本体（本仓库）的改进不靠临时起意：**在项目副本里发生与试点，审核通过后才写回本体**。
> 与既有规则的关系：试点只改项目自己的 `.agent/`（不违反"骨架只在本目录改"）；晋升走审核门禁（不违反"禁平行规则"——写回本体 = 规则进骨架文件，不是另开文档）。

## 状态机

```
登记 → 试点中 → 待审 → 已晋升 / 已驳回
```

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 登记 | 项目内 `.agent/improvements.md` 追加一行 | 满足登记门槛（见下） |
| 试点中 | 改动只落本项目 `.agent/` 与模板文件，登记表记改动摘要 | 提议可以就地试 |
| 待审 | 试点有结论，或改动小到无需试点 | 试点有效 / 一眼可判 |
| 已晋升 | 写回本体（见"晋升操作"） | 五条标准全过 + **用户批准** |
| 已驳回 | 不改本体 | 理由写明：项目特有 / 与既有纪律冲突 / 成熟工具已覆盖 / 口味偏好 |

## 登记门槛（不满足不登记）

1. 规则缺失或冲突造成了**实际返工**（不是"感觉会出问题"）
2. 同类摩擦出现 **≥2 次**
3. **能力缺口**：任务需要某个 skill / MCP / 依赖而环境没有

## 五条审核标准（晋升必须全部成立）

1. **真实性**：登记表有场景与证据，不是假想问题
2. **普遍性**：换一个同骨架项目也会遇到（最好 ≥2 项目出现同类，或逻辑上必然复现）
3. **有效性**：试点验证有效；或改动足够小、风险可一眼判
4. **兼容性**：不与既有纪律/裁决顺序冲突，不制造第二权威，不与成熟工具（Backlog / Spec Kit / Worktrunk）重复造轮子
5. **必要性**：现有条款与工具确实覆盖不了

## 审核方式：evolve

审核工具是骨架库侧的 `evolve.py`（不在 `wsc.py` 里：晋升改的是本体，属开发面，
按 ADR-10 不随分发面走，curl 单文件模式也就带不动它）。对任意 harness 说
**「evolve <项目路径>」**，它应当执行：

1. `python <库>\evolve.py <项目> --rubric` —— 五条标准现读现印，避免两套口径
2. `python <库>\evolve.py <项目> --out 记录.json` —— 机器负责客观维度：状态机合法性、
   同类摩擦跨项目计数（普遍性）、证据列点到的路径/commit 能不能翻出来（真实性）、
   提议落点预判与落点文件已有条款（兼容性提示）
3. AI 只填两个主观维度（**有效性、必要性**）与结论（晋升 / 继续试点 / 驳回），逐条给理由
   ——**驳回是一等公民**，拿不准就驳回
4. 晋升候选先试装再写回：`python <库>\evolve.py --apply-check 补丁.diff`
   （临时副本复制骨架库 → `git apply --check` → 套上跑全套自测 → 再新实例化一个项目跑
   一次全量 `wsc check`；自测变红即拒绝，本体不动）
5. 向用户展示将改哪些本体文件、改什么 → **等用户批准**
6. `python <库>\evolve.py --verify-record 记录.json` —— 机器门禁：结论合法、晋升必须
   两项主观评估齐、四项证据齐（diff 位置 / 来源项目 / 测试运行标识 / 用户批准），
   缺一不得写回

## 晋升操作（写回本体）

1. 改 CoHarness 对应文件：骨架规则改骨架文件、调度改 `ROUTER.md`、工具链改 `wsc.py`
   （新的审核能力才改 `evolve.py`）
2. `docs/CHANGELOG.md` 顶部追加一行：`- YYYY-MM-DD [晋升 I-xxx@来源项目] 改动摘要`，
   并带上 `--verify-record` 要求的三证（diff 位置、来源项目、测试/CI 运行标识）
3. 库内 git commit：**一个晋升一个 commit**
4. 合并后复查（I-004 的最小实现）：写回后至少跑一次 `python -m unittest discover -s tests`
   与 `python wsc.py check <试点项目>`——pre-commit 只在提交当时判，main 上的合成态没人复查
5. 回写项目登记表状态（已晋升 + 日期；驳回 + 理由）；其他已实例化项目**不自动同步**，手动 diff 搬运
6. 同批次试点只晋升一条登记行（一行一个改动，保持 diff 最小）

## 能力缺口通道（skill / MCP / 依赖）

- 登记：类别填"能力"，注明任务场景 + 需要的能力 + 候选名（没有候选写"待选型"）
- 晋升去处：**ROUTER.md"推荐能力"节**（按骨架分组），不写骨架规则文件
- 是 npm/winget 依赖的：同步加进对应骨架的 wsc.py NEXT_STEPS
- 候选选型原则：优先用户已装的；其次官方/活跃开源；README"组件版本与选型记录"里排除过的不复活（如 Vibe Kanban）
