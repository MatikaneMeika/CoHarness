# EVOLUTION-PROCESS — 骨架自我迭代管线

> 本体（本仓库）的改进不靠临时起意：**在项目副本里发生与试点，审核通过后才写回本体**。
> 与既有规则的关系：试点只改项目自己的 `.agent/`（不违反"骨架只在本目录改"）；晋升走审核门禁（不违反"禁平行规则"——写回本体 = 规则进骨架文件，不是另开文档）。

## 状态机

```
登记 → 试点中 → 待审 → 已晋升 / 已驳回
```

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 登记 | 项目内 `.agent/improvements.md` 追加一行 | 满足登记门槛（见下） |
| 试点中 | 改动只落本项目 `.agent/` 与模板文件，登记表记改动摘要 | 提议可以就地试 |
| 待审 | 试点有结论，或改动小到无需试点 | 试点有效 / 一眼可判 |
| 已晋升 | 写回本体（见"晋升操作"） | 五条标准全过 + **用户批准** |
| 已驳回 | 不改本体 | 理由写明：项目特有 / 与既有纪律冲突 / 成熟工具已覆盖 / 口味偏好 |

## 登记门槛（不满足不登记）

1. 规则缺失或冲突造成了**实际返工**（不是"感觉会出问题"）
2. 同类摩擦出现 **≥2 次**
3. **能力缺口**：任务需要某个 skill / MCP / 依赖而环境没有

## 五条审核标准（晋升必须全部成立）

1. **真实性**：登记表有场景与证据，不是假想问题
2. **普遍性**：换一个同骨架项目也会遇到（最好 ≥2 项目出现同类，或逻辑上必然复现）
3. **有效性**：试点验证有效；或改动足够小、风险可一眼判
4. **兼容性**：不与既有纪律/裁决顺序冲突，不制造第二权威，不与成熟工具（Backlog / Spec Kit / Worktrunk）重复造轮子
5. **必要性**：现有条款与工具确实覆盖不了

## 审核方式：evolve

任意 harness 说 **「evolve <项目路径>」**（ZCode/Qoder/Gemini 走 collab-zone skill；Codex 经全局指针读本文件）：

1. 读项目登记表非终态条目（`python <库>\wsc.py improve <项目>` 可机械列出）
2. AI 逐条按五条标准评估：晋升 / 继续试点 / 驳回，逐条给理由——**驳回是一等公民**，拿不准就驳回
3. 晋升候选：向用户展示将改动哪些本体文件、改什么 → **等用户批准**
4. 批准后执行"晋升操作"；能力缺口类走"能力缺口通道"

## 晋升操作（写回本体）

1. 改 CoHarness 对应文件：骨架规则改骨架文件、调度改 `ROUTER.md`、工具链改 `wsc.py`
2. `docs/CHANGELOG.md` 顶部追加一行：`- YYYY-MM-DD [晋升 I-xxx@来源项目] 改动摘要`
3. 库内 git commit：**一个晋升一个 commit**
4. 回写项目登记表状态（已晋升 + 日期；驳回 + 理由）；其他已实例化项目**不自动同步**，手动 diff 搬运
5. 同批次试点只晋升一条登记行（一行一个改动，保持 diff 最小）

## 能力缺口通道（skill / MCP / 依赖）

- 登记：类别填"能力"，注明任务场景 + 需要的能力 + 候选名（没有候选写"待选型"）
- 晋升去处：**ROUTER.md"推荐能力"节**（按骨架分组），不写骨架规则文件
- 是 npm/winget 依赖的：同步加进对应骨架的 wsc.py NEXT_STEPS
- 候选选型原则：优先用户已装的；其次官方/活跃开源；README"组件版本与选型记录"里排除过的不复活（如 Vibe Kanban）
