### 1.1 边界（先读这条，它决定后面所有失败规则）

- **委托记录全在 git**：卡 `status`/`assignee`、`claim` 写的 `branch.<分支>.coharness-card`

### 1.4 失败规则（完整版，这是本轮的语义核心）

**A. 预检阶段（`plan`，零副作用）** —— 五种情况判 `ready=False`，面板把原因写进提示行，
CLI 打印原因并非零退出。因为都发生在任何写操作之前，这一步失败是**完全无痕**的：

1. 没有可派的 todo 卡（非 todo / 已被认领 / 依赖未就绪 / 边界冲突）
2. 卡的边界推不出角色（没落进所有权表）
3. 缺项目侧 `.agent/dispatch.md`
4. 角色在命令表里没有对应行
5. 命令里的工具不在 PATH（附安装提示，面板标灰）

**B. 执行阶段（`launch`，三步串行，任一步失败就地中止）** —— 抛 `SystemExit`，
CLI 退出码 1，面板显示 `[失败] ...`：

1. `wsc claim` 失败（典型是卡刚被别人抢走）→ 不建 worktree、不开窗
2. 建 worktree 失败 → 不继续
3. 拉起失败（终端起不来）→ 只报一次

**C. 三条铁律**

- 不自动重试
- 不改派（绝不换一张卡顶上）
- **不回滚**：认领本身是一个提交。若认领成功但后面失败，卡就停在 `doing`、worktree 可能
  已经躺在那儿。没有事务、没有补偿动作——这是有意的，委托记录只以 git 为准，进程不持有
  "待清理"状态。恢复靠人：`git worktree remove` 清掉，卡改回 `todo`，或按 `r` 重试。

**D. 拉起成功之后就不管了** —— 进程立刻失联。终端里的 CLI 是崩了、卡住了还是干完了，
CoHarness 一律不知道。所以"失败"只覆盖**没能把进程拉起来**，不覆盖**拉起来之后跑砸了**。

**E. 重试的唯一入口** —— 人在面板按 `r`（等价于再派一次），或再敲一遍
`coh-dispatch --advance`。`m` 手动模式只印命令，永不失败。

**F. 覆盖缺口（如实记录）** —— 认领失败、拉起失败、未就绪、工具缺失都有测试钉住；
**"建 worktree 失败"这条路径只有实现、没有专门的测试**。另外 worktree 路径已存在时算
**成功跳过**，不是失败。

## 2. 未决议题：总控（master control）

### 2.1 用户口径

> "每次新开项目后，这个新开项目的**负责权限最高 + 往后推进**的 agent，类似于 ClassObserver
> 的总控的定位。"

用户同时明确：**失败重试不该由 CoHarness 负责，但要有总控负责**——"这样太不智能了"。
即：库侧保持无状态（不重试），但协议层要有一个角色接手失败与重试。

### 2.2 ClassObserver 的实证（只读观测）

ClassObserver 是 03 骨架的实例（2026-09-29 15:06，commit `2e76164`，`pm-zcode`）。
它与 03 骨架默认形态的差异：

| 项 | 03 骨架默认 | ClassObserver 实际 |
|---|---|---|
| 交付树 | `code/` | `project/`（docs 并入 `project/docs/`） |
| 工作层 | 无 | `work/{briefs,evidence,scratch}` |
| 角色结构 | pm / architect / integrator 三个平级行 | **合并成一行"本项目由总控会话身兼"** |
| 规则层所有权 | **所有权表无此行** | `AGENTS.md`、`.agent/`、`work/briefs/` → `architect（总控）` |

关键证据：`git blame` 显示"总控"那一行来自**实例化的第一个 commit `2e76164`**，

## 3. 具体建议与理由

### 3.0 先立四条判据（后面每条建议都按它推）

1. **越线判据**：把 CoHarness 进程杀掉重启，状态一条都不丢。任何建议不得引入"需要常驻
   进程才成立"的调度状态（ADR-11）。
2. **既有条款优先**：能复用 stale / 改派 / ADR / 规则卡的，不新造机制。协议里已经有
   "改派需要正面证据""缺席 ≠ 死亡"，这些是资产不是障碍。
3. **证据门槛**：没到 `EVOLUTION-PROCESS` 门槛的，先登记、继续试点，不硬推。
4. **改动最小**：一个改动一个 commit（CONTRIBUTING 明文），不把独立议题捆在一起。

### 3.1 建议一：本分支先独立合并，合并前补两个测试

**做什么**：把第 1 节的 dispatch 改动单独合并，不与总控议题混在一起。合并前补上：

1. **建 worktree 失败路径**的测试（1.4-F 记录的缺口）
2. **"认领成功但建 worktree 失败 → 卡停在 doing、不自动回滚"**的测试

**为什么**：

- dispatch 分支是独立的、已验证的（最终 367 测试 + 真机冒烟），没有理由等总控议题。
- 第 2 条尤其重要：**"不回滚"是一个反直觉的设计决定**，现在只有实现、没有钉子。
  后续任何一次"顺手把失败清理干净"的重构都会静默改掉它，而症状是"卡被莫名退回
  todo、worktree 被删"——这种 bug 很难从现象倒推回原因。钉住它的成本是十几行测试，
  收益是保住一个语义。

### 3.2 建议二：把"总控"拆成两半，分别走流程

这是本报告最重要的一条建议。现在混在一起的其实是两个不同的东西：

| 议题 | 性质 | 证据状态 | 建议 |
|---|---|---|---|
| **规则层没有写者** | 骨架文件自身不完备 | 与项目内容无关，每个 03 实例都继承 | 可较快论证，走登记 → evolve |
| **"总控"这个角色定位** | 项目形态选择 | 只有 ClassObserver 一个数据点 | 继续试点攒证据，不急着晋升 |

**理由**：

- 03 骨架的 `AGENTS.md` 禁令 2 写着"一切协作规则只在本文件和 `.agent/` 中演进"，
  但所有权表里**没有 `AGENTS.md` / `.agent/` 这一行**。骨架只规定了"改表要走规则卡 + ADR"
  这个流程，**没规定谁执行**。这是文件自身的不完备，与项目内容无关：任何一个 03 实例
  都继承这个洞。论证它不需要第二个项目。
- 而"这些规则该由一个叫总控的会话统一持有"是**项目形态判断**，依赖项目规模与并行度。
  单组件项目可能永远不需要。这条需要第二个数据点，或需要论证"03 骨架必然多 harness
  并行 ⇒ 必然需要唯一裁决者"。
- 拆开之后，第一条可以现在就推进；第二条不会拖住第一条。

**建议的登记内容**（回 ClassObserver 写 I-008）：

- 类别：规则
- 场景：任何 03 项目改 `AGENTS.md` / `.agent/` 时
- 问题：骨架禁令要求规则在这两处演进，但所有权表没有声明写者；实际由实例化会话自行
  发明（ClassObserver 补成 `architect（总控）`，见 commit `2e76164`）
- 提议：03 骨架所有权表新增"规则层"写者行；同时把"总控会话身兼 pm/architect/integrator"
  写成**推荐形态**而非唯一形态
- 证据：`2e76164`（总控首现）、T-050/051/052（总控复核与交接单）
- 状态：登记

### 3.3 建议三：派发模型保持"谁收工谁唤醒"，总控做兜底

**建议**：不改成"总控统一派发"。保持现状——任何 harness 收工都可以 `coh-dispatch --advance`；
总控负责的是**失败处理、巡检、裁决**，而不是当唯一的派发按钮。

**理由**：

1. **单点在场依赖**。如果所有派发都过总控，总控会话一结束，整条链就停——即使 coder
   已经空闲、卡已经就绪。去中心模型下，任何一个收工的 harness 都能踢下一张卡，推进力
   不依赖某一个会话活着。用户对总控的定义是"**往后推进**"——去中心模型在"推进"这件
   事上比中心化更稳。
2. **改动更小**。现状的 `--advance` 已经写在 03 骨架 AGENTS.md 与 parallel-protocol 的
   收工节里。改成中心化还要新造"coder 怎么向总控汇报""总控怎么知道有人汇报了"——
   那是新的状态、新的失败点。
3. **总控的权威不靠"独占派发"体现**。总控仍然是唯一契约记录者、拆卡者、合并收尾者、
   规则层写者。它的最高权限体现在**裁决与规则**，不是体现在按按钮。

**代价要写明**：去中心模型下，"下一步派谁"的决定权分散在各个收工会话里，可能出现
两个人同时派发同一张卡——但这由 `wsc claim` 的原子性兜住（先到先得，被抢者重新 plan），
不是新风险。

### 3.4 建议四：把"失败重试归总控"落成一张契约表

这是用户原始诉求的直接答案——CoHarness 不重试，但**总控要接**。建议写进 03 骨架
parallel-protocol 的收工节：

| 失败 | 归属 | 动作 | 上限 |
|---|---|---|---|
| 卡被抢（认领失败） | 发起派发的会话 | 重新 `plan` 拿新候选，重试一次 | 1 次 |
| 缺表 / 角色无命令 / 工具不在 PATH | 发起会话 | 当场补配置；补不了登记 `.agent/improvements.md` + 升级给人 | 补 1 次 |
| 建 worktree / 开窗失败 | 发起会话 | 重试 | 1 次 |
| 重试到顶 | 发起会话 | 登记 + 升级给人，**不静默改派** | — |
| 派发成功但卡长期无动静 | integrator（总控帽子） | 走既有 stale 条款（24h 提示 / 48h + 正面证据才改派） | — |

**理由**：

- **为什么重试上限是 1 次**：`launch` 已经明说不重试；总控的重试是"判断"而不是机械循环。
  给死上限是防止 agent 陷入重试风暴——尤其"工具不在 PATH"这类配置问题，重试一百次
  也不会变好。
- **为什么"不静默改派"**：既有条款写着"改派需要正面证据""缺席 ≠ 死亡"。如果派发失败
  就自动换卡，等于把"没拉起来"当成"这个人不行"——而卡被抢本来是**正常竞争**，不是
  失败。改派必须走 48h + 正面证据那条路，否则会破坏"一卡一 assignee"的语义。
- **为什么异步失败不新造机制**：24h/48h 与 integrator 改派权**已经在协议里**了。这一轮
  只需要把"派发成功但没动静"这句话接到那条既有流程上，一行引用即可。

### 3.5 建议五：总控不在场 = 停在原地，靠"下次开工巡检"恢复

**建议**：接受"没人开工，链条就停"，并把恢复动作固定成**开工第一步的总控巡检**：
读 doing 卡 + worktree 在场 + 分支进度，发现僵尸派发就按 3.4 表处理。

**理由**：

- 要 7×24 就得常驻进程，那是 RFC-0003 明确否决的第一方案，也是 ADR-11 的越线判据。
  这条不能松。
- 但"停"不等于"卡死"：状态全在 git，下一次任何会话开工时第一步 `wsc.py sync` 就会
  看到 stale 卡与未完成的派发。**无状态换来的正是这个恢复力**——进程死不死都不影响
  事实，只影响"谁来读事实"。
- 把恢复做成"开工巡检"而不是守护进程，成本是文档里几行，收益是把"智能"落在每次
  开工的入口上。

**代价**：如果一直没人开工，链条确实停着。这是设计选择，写清楚，不要当成缺陷。

### 3.7 明确不建议做的事

- **不在本工作树改 03 骨架**：绕过门禁会开"我觉得该改就改"的先例，CONTRIBUTING 说这比
