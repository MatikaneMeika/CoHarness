### RFC-0004：远端门禁——把执法从"君子协定"升格为仓库事实

**状态**：草案（随 W19 零改动版、W20 `--against` 分两步实施）
**决策记录**：ADR-12（`docs/EVOLUTION-PLAN.md`，只增不改）
**前置**：RFC-0003、ADR-10（决定 1"响亮失败"精神贯穿本文降级语义）

#### 1. 背景与问题

本地执法有两个结构性缺口（v2 §1.2）：`git push --no-verify` 直通本地钩子；第二台机器裸克隆
无钩子（`wsc sync` 才补装）。对协作者与新机器而言，唯一共同执法点是远端。

pre-commit 的 `--diff` 判**暂存集**（`check.py:544` 起）；CI checkout 出的是干净树、没有暂存集——
"改动必须挂卡"这条执法在 CI 形态下需要显式基线，否则远端门禁只能拦非法看板与坏文件名，拦不住
卡外改动。

#### 2. 决策

**D1 · workflow 随 03 骨架分发**（承 ADR-12）：01/02/04 不带——03 才是多 harness 执法场景。
`pyproject.toml` package-data 按 `pyproject.toml:59-61` 点文件规则逐条写死；
`tests/test_packaging.py` 与 `tests/test_skeleton_integrity.py` 双钉。

**D2 · 门禁是两级形态，骨架只承诺第一级**（修订，对应审阅 F2）：

| 级别 | 形态 | 谁保证 |
|---|---|---|
| 检测线（默认） | workflow 跑 `check.py`，红=可见信号 | 骨架（文件即能力） |
| 硬门禁 | required status check 绑定 job 名 | 装机操作（§5 一条龙，一次性） |

骨架分发的 workflow 在没有 required check 配置时是**探测器**：push 先被远端接受、CI 后运行、
红了不拦 merge——这是诚实的边界，不是缺陷。骨架不做、也不该做的是代替用户配置其仓库的
branch protection/rulesets（零服务端：文件即真相，配置属于用户仓库侧）。装机操作一条龙见 §5。

**D3 · 事件与基线矩阵**（修订，对应审阅 F1/F3）：

| 触发事件 | 执法基线 | 基线来源 | 说明 |
|---|---|---|---|
| `push`（main） | `github.event.before` | event payload | 普通 push：before = main 旧 tip，必可达 |
| `pull_request`（main） | `origin/main` | fetch 后的远端分支 | checkout 默认检 merge ref，`origin/main...HEAD` 三点 diff = PR 分叉后全部改动 |
| `merge_group`（checks_requested） | `github.event.merge_group.base_sha` | event payload | 队列当前基底；无此触发器则 required check + merge queue 场景**永不报告、PR 卡死**（官方文档 ✓，见 §6.6） |

**D4 · 降级语义：探测可解析性，不做字符串魔法**（修订，对应审阅 F1）：

v2 原案"`event.before` 为全零时降级"**不成立**：全零仅出现在**首推（分支创建）**；强推时
before 是**非零的旧 tip**，且强推后该提交在远端失去引用、runner 的 `fetch-depth: 0` 拉不到它
（不可达对象不在 fetch 结果里）——`--against` 会落进"响亮失败"硬红。这与"门禁不做第二裁判"
（强推是维护者特权，协议另有禁推条款）正面冲突，且计划中的真机矩阵覆盖不到此场景。

修订后的统一算法（伪码，三事件共用）：

```
BASE = <按 D3 矩阵取基线>
if git cat-file -e "${BASE}^{commit}"; then
    check.py --against "$BASE" --names --tasks --no-track     # 增量执法
else
    ::notice "enforcement base unresolvable (first push / force push / shallow clone); running full-surface check"
    check.py --names --tasks --no-track                         # 降级，必须可见
fi
```

一个 `cat-file -e` 同时覆盖三种不可解析情形：全零（首推）、强推后不可达、浅克隆对象缺失。
**可解析的强推**（旧 tip 短期内未 GC、仍可达）会照常增量执法——此时 diff 计算的是"重写实际
改变了什么"，执法它仍是"改动挂卡"，不构成第二裁判。此立场自洽且无需特判。

**D5 · `merge_group` 触发器预置于零改动版**（对应审阅 F3）：未启用 merge queue 的仓库该触发器
永不激活（惰性无害，与"非 GitHub 托管惰性无害"同哲学）；预置可避免 W20 升级时存量用户漏更
workflow。代价：YAML +3 行。

**D6 · 供应链基线**（对应审阅 F4）：

- `permissions: contents: read`（最小权限，+2 行）；
- actions 引用采用 **tag + 版本注释半钉**（`actions/checkout@v4  # v4.x.y`），不写死 40 位 SHA。

  权衡：SHA 全钉更安全，但骨架是模板、写死 SHA 意味着每次上游升级都要改骨架发版，腐烂成本
  高于收益——本 workflow 无 secret 写权限、跑的是用户自己仓库的 `check.py`，威胁模型是
  "防意外不防蓄意"（§6.5）。安全性要求高的仓库可自行替换为 SHA（替换点即 YAML 两处 `uses:`）。

**D7 · `--against` 判定核心复用**（承 W20）：把 `check_diff` 拆成"变更集提供者 + 判定核心"，
`--against` 的变更集 = `git diff --name-status <ref>...HEAD`（改名连旧路径一起过所有权表，
I-005 同口径），喂给**同一判定核心**——不写第二套口径（宪法：判定不另写一套）。重构不改行为：
既有用例零改动仍绿是安全判据。失败语义：基线不可解析时**降级不硬拦**（D4），降级必须可见。

#### 3. 替代方案表（修订版：原 4 行拆 1 增 1）

| 替代方案 | 否决理由 |
|---|---|
| CoHarness 侧在线门禁服务 | 违反零服务端 / 文件即真相（宪法第 1、2 条）；v2 §1.3 新纪律 |
| 只靠分支保护 required check（不配 workflow） | 它保证"有个绿 check"，不保证跑的是本项目执法——绿的可能是个空跑的 job |
| workflow 不配 required check 就宣称"门禁" | 检测器≠门禁：push 先被接受、CI 后运行，坏状态已进 main（审阅 F2）；骨架承诺止于检测线，硬门禁是装机操作（§5） |
| 只加 PR 模板纪律（已有，禁 `--no-verify`） | 约定不是机制——这正是本 RFC 要补的口子 |
| CI 全量跑 check.py 不加 `--against` | CI 干净树无暂存集，`--diff` 空转，"挂卡"执法缺席——所以 W20 必要 |
| 从 PyPI tag 装 coharness 跑包内 check.py（而非用户仓库内文件） | 可防蓄意篡改 check.py（§6.5），但引入版本耦合（包版 ≠ 仓库骨架版）与发布链依赖；威胁模型不要求——登记为未来能力选项，不是当前决策 |

#### 4. 技术规范

##### 4.1 workflow 终稿（W20 形态；W19 = 去掉 probe/增量两步的子集，见 Part B YAML 两版）

```yaml
name: coharness-gate
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  merge_group:            # 惰性无害：未启用 merge queue 的仓库永不触发（RFC-0004 D5）
    types: [checks_requested]
    branches: [main]
permissions:
  contents: read          # 最小权限（RFC-0004 D6）
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4   # v4.x.y；高安全仓库可换 40 位 SHA（D6 替换点 1/2）
        with:
          fetch-depth: 0    # --against 需要基线可达（浅克隆教训 CHANGELOG :11）
      - uses: actions/setup-python@v5  # 替换点 2/2
        with:
          python-version: "3.11"   # 防 runner 预装漂移
      - name: Resolve enforcement base
        id: base
        run: |
          set -eu
          case "${{ github.event_name }}" in
            pull_request) echo "base=origin/main" >> "$GITHUB_OUTPUT" ;;
            merge_group)  echo "base=${{ github.event.merge_group.base_sha }}" >> "$GITHUB_OUTPUT" ;;
            *)            echo "base=${{ github.event.before }}" >> "$GITHUB_OUTPUT" ;;
          esac
      - name: Probe base resolvability
        id: probe
        run: |
          if git cat-file -e "${{ steps.base.outputs.base }}^{commit}" 2>/dev/null; then
            echo "resolvable=true" >> "$GITHUB_OUTPUT"
          else
            echo "resolvable=false" >> "$GITHUB_OUTPUT"
          fi
      - name: CoHarness gate (incremental)
        if: steps.probe.outputs.resolvable == 'true'
        run: python scripts/check.py --against "${{ steps.base.outputs.base }}" --names --tasks --no-track
      - name: CoHarness gate (full, degraded)
        if: steps.probe.outputs.resolvable == 'false'
        run: |
          echo "::notice::enforcement base unresolvable (first push / force push / shallow clone); running full-surface check"
          python scripts/check.py --names --tasks --no-track
```

**行数说明**：v2 预估 ~20 行是 W19 零改动版的口径；W20 终稿约 45 行，膨胀来自 D3 三事件矩阵、
D4 探测步、D5/D6 供应链与 merge queue 预置。workflow 是 YAML 模板，**不占 check.py 的
820 行预算**（LINE_BUDGET 只管执法面单文件）。

##### 4.2 与 pre-push 的口径一致性

CI 与 `pre-push:22` 同跑 `--names --tasks`，W20 起同跑 `--against`——同一判定核心，仅变更集
提供者不同（暂存集 vs 显式基线）。`--no-track`：runner 上写 `.agent/telemetry.jsonl` 既无意义
又污染工作树。

#### 5. 装机操作：从检测线到硬门禁（新增，对应审阅 F2）

骨架装出的是检测线。硬门禁是用户仓库的一次性配置（gh CLI ≥ 2.x，REST rulesets）：

```bash
gh api -X POST /repos/{owner}/{repo}/rulesets --input - <<'JSON'
{
  "name": "coharness-gate-required",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": ["refs/heads/main"] },
  "rules": [
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": false,
        "required_status_checks": [ { "context": "coharness-gate / check" } ]
      }
    }
  ]
}
JSON
```

- **context 名耦合**：`"<workflow name> / <job key>"` = `coharness-gate / check`——改 YAML 的
  `name:` 或 job key 会脱钩，需同步 rulesets。
- 验证：配好后推一例非法看板（同人两张 doing），push 应被拒且提示缺 required check。
- bypass actors 默认不配（管理员也拦）；要配是用户自己的裁决，RFC 不代做。
- 该节以 `03-multi-harness-project/AGENTS.md` "远端门禁"小节的形式随骨架分发（口径：
  本地钩子是第一道门，CI 是第二道；`--no-verify` 逃得过本地、逃不过**启用硬门禁后的**远端——
  未启用时 CI 红是可见信号，不是拦截）。

#### 6. 已知边界（v2 W20 第 7 点要求的成文范围 + 审阅新增）

1. **merge commit 下的 `ref...HEAD`**：三点 diff 从 merge-base 起算。对 `--against before` 的
   push 场景，before 若是上一个 merge commit，diff 含并入分支的全部改动——这正是"这次 push
   实际改变了什么"，语义正确；边界在 rebase 改写历史的场景，此时应见 D4 的强推路径。
2. **强推**：不做第二裁判（协议另有禁推条款），但**降级必须可见**（`::notice`），绝不静默按
   空集全绿（ADR-10 决定 1 同精神：留空和写错是两回事）。可解析的强推照常增量执法（D4 立场）。
3. **首推**：before 全零不可解析 → 降级全量，与强推同路径、同可见性。
4. **浅克隆**：`fetch-depth: 0` 已消除常态浅克隆；若未来有人改回浅克隆，cat-file 探测把对象
   缺失也导入降级路径——不会响亮失败。
5. **check.py 来自被检 HEAD**：workflow 跑的是用户仓库当前 HEAD 的 `scripts/check.py`——
   恶意 PR 可以改 check.py 让它永远绿。**防意外，不防蓄意**（与 R8"不做第二裁判"同一威胁
   模型）；要防蓄意走替代方案表末行（PyPI tag 跑包内 check.py），暂不采纳。
6. **merge queue**：启用 required check 后再开 merge queue 的仓库，若无 `merge_group` 触发器，
   check **永不报告**、PR 卡死在队列（GitHub 官方文档 ✓ 2026-10-03）。D5 预置触发器后此边界
   关闭；`base_sha` 是队列当前基底，语义为"本 PR 在真实队列语境下的增量"。
7. **非 GitHub 托管**：workflow 文件惰性无害；GitLab 等价物登记为未来"能力缺口"（v2 原口径）。
8. **Actions 分钟数**：`fetch-depth: 0` 对中小仓库可忽略；巨型 monorepo 用户可自行改浅克隆 +
   接受降级路径（D4 兜底）。

#### 7. 代价与后果

- 骨架新增一个 `.github/workflows/` 目录（03 only），`maintain.py` 增迁移步 `up_remote_gate`
  （schema 4→5，`_three_way_merge` 先例）。
- check.py 760→820（第三次上调，先例程序：独立 commit + LINE_BUDGET 注释写理由 + CHANGELOG）。
- 用户仓库获得门禁**候选位**：真正的硬门禁需要 §5 一次性装机——这个"骨架不替用户做决定"的
  保留，本身就是零服务端纪律的延伸。

**W19→W20 升级路径**（给执行者的一句话说明，可进 RFC-0004）：升级 = 把最后一步 run 替换为

`fetch-depth: 0`。其余行不动——升级是纯增量 diff。

### B3 · W20 实施形状（第 5 点重写 + 第 7 点扩充）

第 5 点原文（`优化计划书-v2.md:336-338`）：

> workflow 升级：`pull_request` 触发时 `--against origin/main`（`fetch-depth: 0`）；`push`
> 触发时 `--against ${{ github.event.before }}`；`event.before` 为全零（首推/强推）时**降级**
> 只跑 `--names --tasks` 并发 `::notice` 声明降级——降级必须可见，不许静默。

替换为：

> workflow 升级（RFC-0004 D3/D4 定稿）：三事件三基线——`pull_request` 用 `origin/main`、
> `merge_group` 用 `github.event.merge_group.base_sha`、`push` 用 `github.event.before`，统一
> `fetch-depth: 0`；**降级判据从"全零字符串"改为 `git cat-file -e <base>^{commit}` 可解析性
> 探测**——全零只覆盖首推，强推的 before 是非零旧 tip 且强推后不可达，原设计会落"响亮失败"
> 硬红，与"门禁不做第二裁判"冲突。一个探测覆盖首推/强推/浅克隆三种不可解析；降级必须可见
> （`::notice`），不许静默；可解析的强推照常增量执法。

第 7 点原文（`优化计划书-v2.md:340-341`）扩充为：

> RFC-0004 追记第二决策节，成文范围：为何 push 用 `event.before`（D3 矩阵）、强推为何降级
> 不硬拦（D4 立场：可解析性探测 + 可见降级；协议本就禁强推，门禁不做第二裁判）、merge commit
> 下 `ref...HEAD` 语义（§6.1）、**merge queue 耦合**（§6.6：required check + merge queue 无
> `merge_group` 触发器则 check 永不报告、PR 卡死——触发器已在 W19 预置）、**check.py 来自
> 被检 HEAD 的威胁模型边界**（§6.5：防意外不防蓄意）。

W20 验收清单增两条：

- `[ ] 真机：强推一例走降级路径（notice 可见、不硬红）——强推语义的专门钉子：v2 原设计
  （全零判据）在此场景会意外硬红`
- `[ ] 真机（可选，若装了 merge queue）：入队 PR 的 check 正常报告——无则记为欠账附理由`

### C1 · W17 README "How CoHarness relates to other tools" 锚点段（英文终稿，可粘贴）

```markdown
### Why mechanical enforcement?

The 2025 DORA report found that AI adoption now improves delivery
throughput but still increases delivery instability — the bottleneck has
moved from producing code to governing what lands in the repository.
Failure taxonomies for multi-agent LLM systems (MAST, Cemri et al.,
arXiv:2503.13657) reach the same conclusion from the research side: the
largest shares of agent failures are specification and inter-agent
coordination issues, not model capability.

Orchestration tools parallelize agent *processes*; they do not govern
repository *conventions*. Native agent teams remain experimental, expose
no per-agent file permissions, and keep their task lists outside the
repository. CoHarness is the protocol layer underneath any of them: every
agent an orchestrator spawns can work in the same repo, under the same
AGENTS.md, against the same check.py — with claims serialized, paths
owned, and every diff attached to a card.
```

> 编排器并行管理代理进程，不管仓库约定——CoHarness 是它们下面的协议层。
