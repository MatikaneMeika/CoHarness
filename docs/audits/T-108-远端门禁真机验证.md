## 结论

- **红绿两例**：红 B / E / F，绿 A / C；run 链接与日志行如上。
- **卡外改动 PR 被拦且可定位**：E。
- **非法看板 push 红**：F。
- **强推降级不硬红**：D。
- **检测线语义核实**：所有红都是"可见信号"——`main` 未配 required check 时 push 不被拒，红只体现在 Actions 结论，未阻断写入（A–F 的 push 全部成功落盘）。
- **rulesets 硬门禁已补测**：见下节「硬门禁真机验证」。
- **merge queue 端到端：本环境不可验**（可选欠账，附理由）：临时仓为 **user-owned** 仓库，rulesets 的 `merge_queue` 规则被 API 拒（`POST /repos/.../rulesets` → 422 `Invalid rule 'merge_queue'`）；同一请求体把规则换成 `non_fast_forward` 即成功（id 24414601，已删），证明请求形状无误、是该规则对本仓不可用。故「入队 PR 的 check 正常报告」无法在个人仓真机跑；W24 的 `merge_group` 触发器已由本地等价验证覆盖（注入事件两场景，见 `docs/audits/T-108-远端门禁本地等价验证.md`）。

## 硬门禁（rulesets）真机验证（2026-10-03 追补）

> 计划 T-108 可选项（`docs/优化计划书-v2.md:994`）：把「检测线」升级成「硬门禁」真机跑一遍，回填
> RFC-0004 硬门禁节。仓改 public（rulesets 需 Pro/public），装规则集 `coharness-gate-required`
> （id `24413599`，`bypass_actors: []`，`current_user_can_bypass: never`）。

**装机 JSON（修正版，`conditions.ref_name` 为对象形状）**：

```bash
gh api -X POST /repos/{owner}/{repo}/rulesets --input - <<'JSON'
{ "name": "coharness-gate-required", "target": "branch", "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [ { "type": "required_status_checks", "parameters": {
      "strict_required_status_checks_policy": false,
      "required_status_checks": [ { "context": "check" } ] } } ] }
JSON
```

| # | 场景 | 期望 | 实测 |
|---|---|---|---|
| G | 直推 main（无 check 结果的全新 commit） | 被拒 | `remote: error: GH013 ... Required status check "check" is expected.` → `push declined due to repository rule violations` |
| H | 合法 PR #3（check SUCCESS，`context=check`） | 可合并 | `mergeStateStatus=CLEAN` |
| I | 卡外改动 PR #1（check FAILURE） | 被拦 | `mergeStateStatus=BLOCKED` |
| J | 非法看板 PR #2（check FAILURE） | 被拦 | `mergeStateStatus=BLOCKED` |

**关键修正 · required check 的 context 是 job 名，不是 `<workflow> / <job>`**：

- 初装按 RFC-0004 原稿写 `context: "coharness-gate / check"`（workflow `name: coharness-gate`，job key
  `check`）→ 合法 PR #3 的 check 结论 SUCCESS 但 `mergeStateStatus=BLOCKED`（匹配不到 check run）。
- 改回裸 `context: "check"` → 同一 PR #3 立刻 `mergeStateStatus=CLEAN`。A/B 复现两次。
- 机理：rulesets 的 `required_status_checks.context` 对齐的是 **check run 的 `name`**；本骨架 job
  未写 `name:`，check run 名 = job key = `check`。workflow 的 `name:`（`coharness-gate`）只是显示分组。
- 结论已回填 RFC-0004 硬门禁节（context 耦合条 + 装机 JSON + 两级表），五个载体同步改口径。

**F-A 结构性冲突的实证**：场景 G 直接证实——在 main 配 required check 会拒绝认领直推，与
`parallel-protocol.md` 的「认领/状态流转直推 main」协议冲突；默认口径维持「检测线是与认领直推
协议唯一兼容的形态」。
