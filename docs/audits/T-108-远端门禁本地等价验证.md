# T-108 远端门禁本地等价验证（workflow 脚本级）

> 日期：2026-10-02 ｜ 执行：控制器（root）｜ 方法：把 `.github/workflows/coharness.yml` 的
> `run:` 块**原样**搬到本地 bash 里跑，分别在 stub 与真实 `check.py` 上验证分支逻辑。
> 对应计划：`docs/优化计划书-v2.md` W19/W20 / T-108。

## 为什么做这个

T-108 要的是"真机拦过"——临时 GitHub 仓 + push + run 链接。当前分支未推送（用户明确要求先不推），
真机部分做不了。但 workflow 的 `run:` 块此前**只做过 YAML 解析**，那段 bash 分支逻辑从没被执行过；
脚本写错一样会让门禁静默失效。所以先在本地把这段逻辑真跑一遍，作为真机前的等价证据。

## 验证一：分支逻辑（stub `python`，只看选路）

在临时 git 仓里用 `python() { echo "RUN python $*"; }` 替身跑原样 `run:` 块：

| 场景 | `COHARNESS_AGAINST` | 结果 |
|---|---|---|
| 有效基线 | `<base sha>` | `RUN python scripts/check.py --names --tasks --against <sha> --no-track` |
| 首推全零 | `0000…0000` | `::notice::` + 降级为 `--names --tasks --no-track` |
| 基线不可达 | `deadbeef…` | `::notice::` + 降级为 `--names --tasks --no-track` |
| 空值 | `""` | `::notice::` + 降级为 `--names --tasks --no-track` |

四条选路全部符合 RFC-0004 的声明。

## 验证二：真实 `check.py`（本地等价 T-108）

用 `wsc.py init 03` 在临时目录实例化项目，`git init` + 首次提交作基线，再跑同一个 `run:` 块
（这次是真 `python scripts/check.py`）：

| 场景 | 命令路径 | 真实输出 | 退出码 |
|---|---|---|---|
| A 卡外改动 | `--against <base>` | `[改动挂卡] 改动未挂任何任务卡: unowned.txt` | **1（拦下）** |
| B 首推全零 | 降级 `--names --tasks` | `::notice::` + `[命名规范] 通过` / `[任务卡] 无任务卡` | 0 |
| C 基线不可达 | 降级 `--names --tasks` | `::notice::` + `[命名规范] 通过` / `[任务卡] 无任务卡` | 0 |

"挂卡放行"这一条由 `tests/test_check_current.py::AgainstBaseline::test_change_covered_by_a_doing_card_passes`
（真实 `check.py`）覆盖，此处不重复造。

## 结论

- **本地等价成立**：workflow 的 bash 分支逻辑 + 真实 `check.py` 在"卡外拦 / 降级可见"两类行为上
  与 RFC-0004 口径一致；卡外改动确实被远端门禁拦下。
- **仍欠真机**：GitHub Actions runner 上的实际运行（`actions/checkout` 取历史、`event.before` 真值、
  run 链接）未做——需要临时仓 + push，属外部副作用，等用户批准后再补 W19/W20 的 run 链接。
- **边界**：本地用的是 Git for Windows 的 bash，与 runner 的 bash 版本可能有差异；本记录**不**声称
  等同于真机 run。
