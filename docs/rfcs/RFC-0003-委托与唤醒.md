# RFC-0003 — 委托与唤醒：`dispatch` 门面 + 面板控制台

- 状态：采纳（本轮实现）
- 日期：2026-10-01
- 提出人：用户（本仓库维护者），触发点是"手动派发任务太累，tui 能不能一键把下一个 harness 拉起来"
- 落点：新增 `dispatch.py`（委托与唤醒门面）+ `docs/rfcs/RFC-0003`（本文件）；`panel.py` 加派发页、
  `board.py`/`board_render.py` 加对应渲染与导航；`pyproject.toml` 加 `coharness-dispatch` / `coh-dispatch`；
  `SECURITY.md` 第 12 条与 `docs/EVOLUTION-PLAN.md`（ADR-11）改口径；03 骨架 `AGENTS.md` 与
  `.agent/workflows/parallel-protocol.md` 收工节各加一行 `coh-dispatch --advance`，并新增
  `.agent/dispatch.md` 启动命令表模板；**不改** `wsc.py`、`scripts/check.py` 的判定逻辑

## 问题

1. **委托已经有了，"唤醒"还缺一半**。03 骨架把"谁在做哪张卡"写进了 git（卡 `status`/`assignee`、
   `claim` 写的 `branch.<分支>.coharness-card` 绑定、worktree 在场），但把人从"看板显示下一张卡可领"
   推到"那个 harness 真在跑"这一步，全靠手敲：认领一条命令、建工作树一条命令、切到新终端再一条。
2. **手动派发是重复劳动，且容易漏步**。漏认领直接干活、漏建工作树跟别人共居一个 clone，
   都是协议明令禁止却没人拦得住的动作。
3. **面板只能看，不能做**。RFC-0002 把面板定成"只读展示面"，看得到候选却动不了手；
   用户的原话是"tui 正式加入控制面板的功能"。

## 约束

- **不做监督进程**（ADR-11）：不能引入"需要常驻进程才成立"的调度状态。委托记录留在 git，
  唤醒是无状态的一次性动作——拉起后立刻失联，不持有句柄、不读子进程输出、不记运行时状态。
- **不另写一套判定**：候选与边界冲突复用项目自己的 `scripts/check.py`（`board.load_check` 装载）
  与 `wsc claim`，不在门面里重写卡片解析或认领规则。
- **不自主决定**：预选必须是写死的确定性规则（同输入同输出），人可随时覆盖。
- **分发面纯标准库、零网络**（`SECURITY.md`）：`dispatch.py` 只许 import 标准库与同目录自带模块。
- **行数上限**：`dispatch.py` ≤300 行；`panel.py` 300 上限不动（增量靠把渲染挪进 `board_render.py` 消化）。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 做成常驻调度器（后台进程轮询看板、自动派发、收结果） | 越线：状态从 git 挪进进程内存，进程一死调度状态就丢；也把"谁决定下一步"从协议挪进程序。这正是 ADR-11 要挡的 |
| 派发时读子进程输出、记录 PID/日志、失败自动重试 | 同样是运行时状态；且"失败自动重试"会静默改派，与"失败不改派、重试只由人触发"冲突 |
| 把启动命令表放进库侧（库知道各 CLI 的名字） | 库侧不该知道下游用什么工具；命令表是项目事实，放项目侧 `.agent/dispatch.md` |
| 复用 `wsc.py` 加 `wsc dispatch` | 分发面已封顶 1250 行且是 curl 单文件承诺，新命令按 ADR-10 归位；派发也不属于"装机与开工" |
| 预选用"最近更新"或随机 | 不可复现，两个人跑同一份看板会得到不同结果；协议里写死"依赖就绪的 todo 里取卡号最小" |

## 决定

- **新门面 `dispatch.py`**：`candidates`（todo + 依赖就绪 + 边界不与在做卡冲突）、`pick`（确定性预选）、
  `plan`（推角色 → 解析命令 → 探工具）、`launch`（认领 → 建工作树 → 开新终端，**唯一副作用点**）、
  `advance`（plan + launch，供协议步骤调用）。缺命令表只列候选、不执行，并响亮提示缺表。
- **唯一新增配置**：项目侧 `.agent/dispatch.md`，Markdown 表格 `角色 → 启动命令`，支持 `{worktree}`/`{card}`。
- **面板升级为控制台**：任务页按 `d` 进派发页；系统预选高亮，↑↓ 改选，Enter 派发，
  `m` 只印命令不执行，`r` 原地重试。面板调用 `dispatch` 的函数，不重复实现机制。
- **收工唤醒是协议动作，不是 git hook**：03 骨架的收工节加一行 `coh-dispatch --advance`。
  钩子互派不做自动链——链条怎么走由协议决定。

## 后果

- **代价：展示面"只读"这条旧承诺作废**。`SECURITY.md` 第 12 条由"展示面只读"改为
  "展示面默认只读，派发是唯一写路径"；`tests/test_panel.py` 的四条只读钉子同步改成"除派发路径外只读"，
  并新增一条"派发路径确实会产生写入"。这是本 RFC 最需要记账的一笔。
- **收益**：看板从"看得到"变成"动得了手"，且动作只有一条路径、一步不漏（认领 + 工作树 + 拉起）。
- **风险与兜底**：`launch` 失败（卡被抢、工作树建失败、拉起报错）一律只上报，不重试、不改派——
  重试只由人在面板里按键触发。越线判据（进程杀掉重启状态不丢）写进 ADR-11，供后续改动自查。

## 追记（2026-10-01）：主机发现与自动派发边界

- 新增项目侧只读探测 `scripts/dispatch_env.py`：从 `.agent/dispatch.md` 读取候选清单与角色命令，只探 PATH，不执行候选 CLI、不联网、不改映射。
- 候选 harness 是环境事实，不是库侧或骨架默认值；骨架只给空清单和填写说明，具体 CLI 名称/路径由 architect 按本机探测或用户指定。
- 自动派发默认关闭。只有用户明确要求 architect 或 integrator“开启自动派发/关闭自动派发”时，才更新项目侧开关；候选可用不等于授权自动改派。
- 不新增“总控”角色；能力拆给既有 architect（候选与映射）与 integrator（只读巡检），库侧分发面仍不知道“总控”概念。
