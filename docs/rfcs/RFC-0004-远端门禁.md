# RFC-0004 — 远端门禁：workflow 随 03 骨架分发（零代码版）

- 状态：采纳（本轮实现）
- 日期：2026-10-02
- 提出人：优化计划书 v2 §1.2 缺口盘点（用户 + 维护者复核）；证据链：`docs/优化计划书-v2.md` §1.2 / W19、CHANGELOG 2026-09-29 I-004 条（pre-push 立门时的绕过面盘点）
- 落点：新增 `03-multi-harness-project/.github/workflows/coharness.yml`；03 骨架 `AGENTS.md` 执法节加「远端门禁」小节；`pyproject.toml` package-data 加 `0*/.github/workflows/*.yml`；`tests/test_skeleton_integrity.py`、`tests/test_packaging.py` 各加钉子。**不碰执法面本体**：`scripts/check.py`、两个钩子、`maintain.py` 一行不改。

## 问题

1. **`--no-verify` 直通**：本地 pre-commit / pre-push 是 git 钩子，`git commit --no-verify` / `git push --no-verify` 原生就能绕过。PR 模板写着禁 `--no-verify`，但约定不是机制——真用了没人拦。
2. **裸克隆无钩子**：钩子装在 `.git/hooks`，clone 不携带；`wsc sync` 会补装，但"新协作者 / 第二台机器先裸提交一批"的窗口一直在。I-004 为 merge/rebase 凑出的非法看板立的 pre-push，也仍然是本地门。
3. **对协作者和第二台机器，唯一共同的执法点是远端**：本地各台机器的钩子可以各自缺席，push 进 main 的那一头不能缺席。

> 注（2026-10-03 W25）：开箱默认只提供**检测线**；**硬门禁**是装机选项，与认领直推协议的结构性冲突与三条出路见下方「追记：W25 两级门禁与硬门禁装机」。

## 约束

- **零服务端、文件即真相**（宪法第 1、2 条）：门禁必须是一个随骨架分发的文件，不许引入 CoHarness 侧在线服务。
- **不写第二套判定**：CI 跑的就是项目自己的 `scripts/check.py`，口径与 pre-push 同源（`--names --tasks`）。
- **打包规则**：unix glob 的 `*` 不匹配点开头的名字，`.github` 这类点目录必须逐条写死（`pyproject.toml` 既有注释先例）；漏一条 pip 装出来的骨架就缺文件。
- **声明的路径必须真存在**：新文件进骨架就要进 `AGENTS.md` 的声明面，由 `tests/test_skeleton_integrity.py` 钉住。

## 备选方案

| 方案 | 做法 | 代价 | 否决理由 |
|---|---|---|---|
| A 什么都不做 | 维持本地钩子 + PR 模板纪律 | 零改动 | `--no-verify` 与裸克隆两条绕过路径继续敞开；协作者与第二台机器没有任何共同执法点 |
| B CoHarness 侧在线门禁服务 | push 后调库侧 API 校验看板 | 服务端 + 网络依赖 | 违反零服务端 / 文件即真相（宪法第 1、2 条）；优化计划书 §1.3 新纪律明令禁止 |
| C 只靠分支保护 required check | 仓库设置把某个 check 设为必需 | 零文件改动 | 它只保证"有个绿 check"，不保证跑的是本项目执法；只能写成"装机后建议"，不是骨架能力 |
| D 只加 PR 模板纪律（已有，禁 `--no-verify`） | 模板多写几行警告 | 零改动 | 约定不是机制——这正是本 RFC 要补的口子 |
| E CI 全量跑 `check.py` 不加 `--against` | workflow 直接全量执法 | 看似更严 | CI checkout 出的是干净树、无暂存集，`--diff` 空转，"改动挂卡"执法缺席——所以 W20 必要 |
| **F（采纳）** workflow 文件随 03 骨架分发 | 见「决定」 | 被牺牲掉的东西见「决定」 | — |

## 决定

`03-multi-harness-project/.github/workflows/coharness.yml`（~20 行）：

```yaml
name: coharness-gate
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: CoHarness gate (names + tasks)
        run: python scripts/check.py --names --tasks --no-track
```

- **口径 `--names --tasks --no-track`**：与 pre-push 同源，不另写判定。CI 一律 `--no-track`——runner 上写 `.agent/telemetry.jsonl` 既无意义（没有 `wsc stats` 消费方）又会污染干净工作树。
- **`setup-python` 钉 3.11**：防 runner 预装漂移。不装 setup-python、直接用 ubuntu 预装 python3 也可行，但在把"依赖 runner 预装"写进承诺之前先钉版本。
- **checkout 默认浅克隆够用**：`--names` / `--tasks` 不读 git 历史；W20 的 `--against` 才需要 `fetch-depth: 0`（浅克隆教训：CHANGELOG 2026-10-01「CI 浅克隆假红修复」条）。
- **只随 03 分发（01/02/04 不带）**：03 才是多 harness 执法场景；单 harness 骨架没有"多工具互踩"要防。
- **被牺牲掉的东西**：
  1. 本版只拦非法看板与坏文件名，拦不住"改动没挂卡"（CI 干净树无暂存集）——W20 用 `--against` 补，代价是 check.py 行数预算 760→820（第三次上调，按先例程序成文）；
  2. GitHub 专用——非 GitHub 托管时该文件惰性无害，GitLab CI 等价物是未来"能力缺口"登记，不在本计划；
  3. 私有仓消耗 Actions 分钟数（job 秒级，可忽略；公开仓免费）。

## 追记：W20 `--against` 基线执法（2026-10-02）

W20 已把 CI 从"只跑 names/tasks"升级为带基线的 diff 执法，判定核心仍只有一套：

- **PR 事件**：`--against origin/main`。`actions/checkout` 改为 `fetch-depth: 0`；浅克隆只能看到干净树，无法计算 `origin/main...HEAD`。
- **push 事件**：`--against ${{ github.event.before }}`。`event.before` 是这次推送前 main 的位置，正好覆盖"直接推 main"的变更集。
- **首推 / 强推降级**：`event.before` 为全零，或 force-push 后旧提交已不可达（`rev-parse` / `merge-base` 失败）时，不静默当作空集；发 `::notice::` 后只跑 `--names --tasks`。降级必须可见，协议本身禁强推，门禁不做第二裁判。
- **已知边界**：`ref...HEAD` 在 merge commit 下按合并基计算；极端 rebase 后基线可能不是发布者脑中的那条历史。判定仍是同一套，边界留在这里，不在 workflow 里写特例。
- **测试钉子**：`tests/test_check_current.py::AgainstBaseline` 三条（卡外拦 / 挂卡放 / 基线缺失响亮失败）；`tests/test_skeleton_integrity.py` 钉住 `fetch-depth`、`--against` 和可见降级。

## 追记：T-123 merge_group 预置与最小权限（2026-10-03）

阶段四 W24 把 workflow 模板补成可安全预置在 merge queue 仓库里的形态，schema 仍为 5，
不另升迁移步——schema 5 尚未发布，v1.2.3 用户升级时 `up_remote_gate` 会直接复制新版 workflow。

- **触发器**：`push` / `pull_request` 之外预置 `merge_group`（`types: [checks_requested]`、
  `branches: [main]`）。未启用 merge queue 的仓库该事件永不激活，惰性无害；启用 required check
  后若缺此触发器，check 永不报告、PR 会卡在队列（附录 B.5 的官方文档核验）。
- **基线**：`merge_group` payload 没有 `event.before`，因此表达式加第三支
  `github.event.merge_group.base_sha`；不修则该事件恒走空基线降级，触发器预置就失去意义。
- **最小权限**：顶层 `permissions: contents: read`；workflow 不需要写仓库内容，默认 token 权限面
  不应继续放大。
- **Actions 半钉**：`actions/checkout@v4  # v4.x.y`、`actions/setup-python@v5  # v5.x.y`。
  SHA 全钉更安全，但骨架是模板，每次上游补丁都要求改骨架发版会把腐烂成本推给所有下游；
  本 workflow 无 secret 写权限、威胁模型是防意外不防蓄意，高安全仓库可自行替换为 40 位 SHA。
- **本地等价证据**：`docs/audits/T-108-远端门禁本地等价验证.md` 已复跑原四场景，并注入
  `COHARNESS_AGAINST` 模拟 merge_group 可解析 / 不可解析两场景；GitHub 表达式短路求值与真实
  merge queue payload 仍属真机边界，本地不冒充真机。
- **试点漂移记录**：PoseWise_Health 只读核对为 schema 3、无 `.agent/skeleton.lock`、无
  `.github/workflows/coharness.yml`；本轮不修改它。其 workflow 将在项目自行运行 `maintain.py`
  `migrate` 时获得新版模板，试点侧不手工补 diff。

## 追记：W25 两级门禁与硬门禁装机（2026-10-03）

W19/W20 落地的是**检测线**，不是天然的门禁：未配 required check 时 push 先被接受、CI 后跑，
红了只可见、不拦合并。把检测线写成天然硬门禁是过度承诺，本追记把口径改成两级：

| 级别 | 形态 | 谁保证 |
|---|---|---|
| 检测线（骨架默认） | workflow 跑 `check.py`，红=可见信号，push 不被拒 | 骨架（文件即能力） |
| 硬门禁（装机选项） | required check 绑 job 名 `check`，红才拦合并 | 用户仓库 rulesets |

口径补充：`--no-verify` 逃得过本地；未配 bypass actors 时，逃不过启用硬门禁后的远端。若用户自行配置 bypass actors，管理员仍可绕过——那是用户仓库的策略，RFC 不代做。

### 硬门禁装机（一次性，用户仓库侧）

```bash
gh api -X POST /repos/{owner}/{repo}/rulesets --input - <<'JSON'
{
  "name": "coharness-gate-required",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": {
      "include": ["~DEFAULT_BRANCH"],
      "exclude": []
    }
  },
  "rules": [
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": false,
        "required_status_checks": [ { "context": "check" } ]
      }
    }
  ]
}
JSON
```

- **JSON 形状**：`conditions.ref_name` 必须是 `{"include": [...], "exclude": [...]}` 对象，
  不是裸数组（外部审阅稿包原稿的 F-B 错误；照抄会被 REST 422 拒）。
  `strict_required_status_checks_policy` 是必填布尔。
- **context 名耦合（2026-10-03 真机修正）**：required check 的 `context` 必须与 **check run
  的 `name`** 逐字一致。本骨架 job 未写 `name:`，check run 名 = job key = **`check`**；因此
  context 是裸 **`check`（job 名）**，**不是** `<workflow name> / <job key>` 形态。真机 A/B
  （临时仓，同一 PR，check 结论 SUCCESS）：`context=check` → `mergeStateStatus=CLEAN`；
  `context=coharness-gate / check` → `BLOCKED`（匹配不到该 check run，直推也被拒）。→ 改
  workflow 的 **job key**（`jobs.<key>`）必须同步 rulesets，否则脱钩；workflow 的 `name:`
  （`coharness-gate`）只是显示分组，不参与 context。落库后务必用一个测试 PR 验证：
  `mergeStateStatus` 转 `CLEAN` 即 context 正确（证据：`docs/audits/T-108-远端门禁真机验证.md` 硬门禁节）。
- **F-A 结构性冲突**：required check 对 main 的**任何**变更生效，而认领/状态流转协议要求
  直推 main（`parallel-protocol.md`）——全新 commit 不可能在推送前就带 check 结果。三条出路：
  1. **bypass actors** 配操作账号：硬门禁退化为只拦 PR 流量，认领直推回到检测线；诚实但弱。
  2. **协议改走 PR**：伤筋动骨，需独立 RFC，不在本计划。
  3. **只对走 PR 合流的分支开硬门禁**：main 仍走直推检测线。
  **默认口径：检测线是与认领直推协议唯一兼容的形态**；硬门禁是用户自己的装机裁决，本 RFC 不代做。
- **bypass actors 默认不配**：管理员也拦；要配是用户仓库的策略，不写进模板。
- **五载体一口径**：workflow 首行、03 `AGENTS.md`「远端门禁」小节、`maintain.py`
  `up_remote_gate` 注入的小节、本 RFC、双语 README。其中 `maintain.py` **不硬编码**该小节——
  它从当前骨架 `AGENTS.md` 用 `_section` 读取后注入，因此与载体②结构同源；
  `tests/test_maintain.py` 断言注入文本与骨架小节逐字一致，`tests/test_skeleton_integrity.py`
  断言五载体都含两级关键词。
