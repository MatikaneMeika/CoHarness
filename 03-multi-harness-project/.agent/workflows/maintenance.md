# 流程：maintenance（依赖升级 / 环境迁移）

适用：升级依赖版本、换运行时、迁移构建工具。特点：**不改业务语义**，改动应可机械验证。

## 步骤

### 1. 影响面评估
- 列出：升什么、从哪个版本到哪个版本、breaking changes 清单（读官方 changelog）
- 涉及锁文件的，锁文件策略先定（谁生成、谁审）

### 2. 隔离分支
- 一卡一分支：`chore/T-xxx-<依赖名>-<版本>`
- 禁止在业务功能分支里夹带依赖升级

### 3. 升级 + 全量回归
- 升级 → 全量 `{{TEST_CMD}}` → 主链路冒烟
- API 变化导致的适配代码：最小化、集中化（适配层一处改，不散落各处）

### 4. 记录
- CHANGELOG：[升级] 依赖名 旧版本 → 新版本 + 原因
- breaking change 或换技术路线 → ADR（docs/DECISIONS.md）
- 适配中发现的业务 bug → 开独立修复卡，不夹带

### 5. 回滚预案
- 升级前记录回滚方式（revert commit / 旧锁文件）；回归不过就回滚，不带病合入

## 多组件注意

各组件依赖**分组件分批升**（先后端再前端之类），一批一回归，禁止一口气全升。
