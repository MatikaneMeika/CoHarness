# CONSTITUTION-SOURCE — 项目原则底稿（供 /speckit-constitution 灌入）

> **底稿定位**：本文件是骨架侧的模板。项目实例化后，把本文内容灌入 `/speckit-constitution`，
> 此后项目运行时的**唯一权威源是 spec-kit 生成的 constitution**，本文不再演进；
> 规则修订一律改 constitution 并 git commit，禁止在本文件另起第二份。
> AGENTS.md 的"全局禁令"节与本稿同源，实例化时以灌入结果为准。

## 项目原则（按优先级排列）

### 原则一：文件即真相

一切约定、状态、决策以仓库内 git 版本化的文件为唯一事实；会话中的口头约定、
工具会话记忆不作为事实来源。每个事实（口径、版本号、结构描述）只在一处记录，
其他地方引用而非复制。

### 原则二：单写者所有权

任何路径前缀在同一时间只有一个唯一写者（见 AGENTS.md 所有权表）。
两任务 allowed_paths 有交集即不得并行；需要越权先回流程开卡，禁止直接动手。

### 原则三：认领唯一与状态纪律

一任务卡最多一个 assignee；一 harness 同时只持有一张 doing 卡。
认领与状态流转的提交直接进共享分支 main；代码改动走功能分支。

### 原则四：交付纪律

交付文件名禁带版本/副本后缀（-v2 / -final / -副本 / -新 / -修正版），
版本由 git tag 与 CHANGELOG 记录；过程产物（草稿、截图、日志、备份）不进交付树；
禁平行规则文档——改规则 = 改文件 + commit，不散落"更正说明"。

### 原则五：方案落档与决策只增不改

口头方案不作数，coder 只认文件；接口契约、架构边界只在唯一契约文件与
ARCHITECTURE.md 演进；一切破坏性变更决策写 ADR（只增不改，被取代的行保留并注明取代编号）。

### 原则六：机械门禁先于人审

`scripts/check.py`（命名规范 / 卡格式与边界节 / 改动挂卡 / 认领冲突）是所有
harness 提交的强制门禁（pre-commit）；实现与审查必须分开两轮；reviewer 清单
全过 + 回归全绿才允许合入。

## 反模式（constitution 明令禁止）

- 门禁未批先开工；两卡改同一文件并行
- reviewer 由该卡实现者兼任
- 用"另写一份说明文档"解决规则分歧
- 注释掉报错、删断言、静默吞异常来"让测试变绿"
- 合并时顺手改代码
